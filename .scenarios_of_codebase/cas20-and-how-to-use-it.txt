CAS20 and how to use it
core/vm/cas20.go:21
CAS20 is implemented as native stateful precompiles, not deployed Solidity token bytecode. The factory is 0xCA5F000000000000000000000000000000000000; ActivationRegistry is 0x7020000000000000000000000000000000000001; PolicyRegistry is 0x7020000000000000000000000000000000000002. Users send ABI-encoded calls to these addresses or a created token address. Variant 0 is Asset; variant 1 is Stablecoin.
core/vm/evm.go:65
First prerequisite: the selected block must have Jenner active on a BSC chain. evm.precompile resolves CAS20 addresses to native handlers only when this gate is open. This walkthrough describes this checkout; it does not assert that a particular public network has activated Jenner. Check the target node and chain configuration before trying the calls.
core/vm/cas20_genesis.go:13
Registry initialization plants marker code 0xEF so the registry accounts persist and GovHub sees code when forwarding governance parameter changes. This does not appoint an administrator or activate features. Do not confuse seeded accounts, fork activation, and feature activation: they are separate prerequisites.
core/vm/cas20_activation.go:144
Governance appoints the activation administrator through updateParam("admin", packedAddressBytes). Only params.CAS20GovHubAddress (0x0000000000000000000000000000000000001007) may call it, and the value must be exactly 20 nonzero-address bytes, not a 32-byte ABI address word. An ordinary wallet cannot appoint itself by calling this method.
core/vm/cas20_activation.go:26
Second prerequisite: query isActivated(bytes32) with keccak256 of the UTF-8 feature name: bsc.cas20_asset, bsc.cas20_stablecoin, or bsc.policy_registry. The appointed activation admin sends activate(bytes32) for each needed feature. Token creation needs its variant feature; policy writes need the registry feature. Deactivation blocks the gated operations but does not disable existing token transfers.
core/vm/cas20_factory.go:40
Predict a token using an eth_call to getCAS20Address(uint8,address,bytes32) on the factory, supplying variant, actual factory caller, and salt. The address is 0xCA52, eight zero bytes, the variant byte, then nine bytes from keccak256(abi.encode(creator,salt)). A wrapper contract becomes creator when it calls the factory. Metadata is not in the address derivation; reuse of the same caller, variant, and salt collides.
core/vm/cas20_factory.go:230
Prepare params as ABI encoding of ONE dynamic tuple. Asset tuple type is (uint8,string,string,address,uint8), containing version 1, name, symbol, initialAdmin, decimals (6 through 18). Stablecoin tuple type is (uint8,string,string,address,string), containing version 1, name, symbol, initialAdmin, currency; decimals are fixed at 6 and currency must be nonempty uppercase ASCII letters, for example USD. The outer tuple offset is required; encoding five separate top-level arguments is different.
core/vm/cas20_factory_test.go:20
Concrete SDK recipe, using ethers-style pseudocode: params = AbiCoder.defaultAbiCoder().encode(["tuple(uint8,string,string,address,uint8)"], [[1,"Demo Asset","DEMO",admin,18]]). For Stablecoin replace the final uint8 field with string, use "USD", and choose variant 1. Each initCalls element is complete function calldata (four-byte selector plus arguments), encoded against the token ABI.
core/vm/cas20_factory.go:109
Send a zero-value transaction to factory.createCAS20(variant,salt,params,initCalls), with ABI return type address. A minimal Asset example uses variant 0 and initCalls=[]; it starts with zero supply, the chosen default admin, no other granted roles, and default supply cap 2^128-1. FeatureNotActivated, malformed parameters, invalid decimals/currency, occupied target, read-only execution, or insufficient gas can prevent creation. Use eth_call/eth_estimateGas to simulate first; send a transaction to persist changes.
core/vm/cas20_factory.go:167
Creation writes marker code and token metadata, initializes the variant extension, emits CAS20Created, and grants the nonzero initialAdmin DEFAULT_ADMIN_ROLE. Ordered initCalls execute in a factory bootstrap context using the complete variant dispatcher. Bootstrap bypasses role and transfer-side policy checks but still enforces mint receiver policy, pause/supply limits, and the permanent role-management freeze after last-admin renunciation. A failed initialization makes the enclosing creation call fail; normal EVM rollback undoes its writes and logs.
core/vm/cas20_factory_test.go:72
The existing test is an executable create-and-use example: predict the address, initialize with grantRole(MINT_ROLE,minter) and mint(alice,1000), create the token, then verify initialization and balances. Bootstrap allows the initial mint without first granting the factory MINT_ROLE. To inspect this path locally, run go test ./core/vm -run "^TestCAS20Factory$" -count=1; this is a suggested command, not a test result from this walkthrough.
core/vm/cas20_admin.go:11
For a token created with empty initCalls, the admin first sends grantRole(bytes32,address) with role keccak256("MINT_ROLE") and the intended minter. DEFAULT_ADMIN_ROLE is bytes32(0); holding it does not itself confer MINT_ROLE. The token also exposes MINT_ROLE() and hasRole(bytes32,address) for discovery and verification. Keep initialAdmin nonzero for this administrable example; a zero admin deliberately leaves no ordinary path to add roles later.
core/vm/cas20_admin.go:436
The granted minter sends mint(address,uint256) to the TOKEN address, with zero native value. For the 18-decimal Demo Asset, mint(alice,100000000000000000000) creates 100 whole tokens; for a 6-decimal Stablecoin, 100 whole tokens is 100000000 units. Mint checks role, pause, recipient policy, and cap, updates balance and totalSupply, and emits Transfer from address zero. Token quantities are integers in base units.
core/vm/cas20_token.go:175
Alice can now send transfer(bob,1000000000000000000) to move one 18-decimal Demo Asset token. Use eth_call for balanceOf(address), totalSupply(), name(), symbol(), and decimals(); use a signed transaction for transfer. The transfer checks pause, nonzero addresses, sender/receiver policies, and sufficient balance, updates both balances, and emits Transfer. With default policies (ID 0), the transfer policy checks allow everyone.
core/vm/cas20_token.go:191
For delegated spending, Alice sends approve(spender,amount); the spender then sends transferFrom(alice,bob,amount). The implementation checks allowance before executor policy, skips allowance decrement for uint256 maximum approval, and applies sender and receiver policies during movement. An allowance does not bypass compliance restrictions. A failed call rolls back changes, including any allowance decrement performed before a later policy or balance failure.
core/vm/cas20_policy.go:66
To add compliance, activate bsc.policy_registry first, then send createPolicyWithAccounts(policyAdmin,1,[alice,bob]) to PolicyRegistry to create an allowlist (type 1; type 0 is blocklist). Obtain its uint64 ID from the simulated return or creation event and confirm the transaction result. The policy admin manages membership; token administrators separately choose whether a token references that shared policy. Policy IDs include type bits, so preserve the full uint64 value.
core/vm/cas20_admin.go:579
The token default admin sends updatePolicy(bytes32,uint64), for example using the scope returned by TRANSFER_RECEIVER_POLICY() and the new allowlist ID. Only listed recipients then pass that receiver policy. Other scopes control transfer sender, delegated executor, mint receiver, seizure exemption, and seizure receiver; their semantics differ, so configure each deliberately. Policy ID 0 is always allow. Binding a policy does not grant permission to edit its shared registry membership.
core/vm/cas20_admin.go:387
Grant PAUSE_ROLE and UNPAUSE_ROLE separately before using pause(uint8[]) and unpause(uint8[]). Feature numbers are 0 transfer, 1 mint, 2 burn, and 3 seize; pause([0]) stops transfers without necessarily stopping minting. burn(uint256) requires BURN_ROLE and burns the caller's balance. Administrative token controls are distinct from the global feature-activation switches.
core/vm/cas20_asset.go:156
Asset adds configurable decimals, multiplier/scaled-balance helpers, UI amount conversion, metadata, and announcements. Stablecoin instead fixes decimals at 6 and exposes currency(). Basic balanceOf/transfer amounts remain raw base units; applications displaying Asset UI/scaled values should inspect the variant helpers and convert explicitly rather than passing a display amount directly to transfer.
core/vm/cas20.go:89
Every CAS20 entry point rejects delegate-style invocation and nonzero native value and charges calldata gas. Call from a wallet or use a normal contract CALL; use STATICCALL only for reads. Even though RequiredGas returns zero, actual execution is metered inside RunStateful for storage, account access, hashing, logs, and other work. Sending BNB as token-call value produces NonPayable rather than buying or minting tokens.
core/vm/cas20_errors.go:39
CAS20 custom errors are ABI revert data, returned with ErrExecutionReverted; inspect them when a simulation fails. Common causes are missing role, paused feature, policy rejection, insufficient allowance/balance, supply cap, malformed ABI, and closed activation gate. Out-of-gas remains an execution resource error. Merely matching the CAS20 address prefix does not prove a token exists: initialized token calls require the exact 0xEF marker hash.
internal/ethapi/api_cas20.go:19
Inspect a created token with JSON-RPC {"jsonrpc":"2.0","id":1,"method":"eth_getCAS20TokenInfo","params":["<token-address>","latest"]}. The response aggregates metadata, variant, supply, cap, pause flags, policy bindings, and variant-specific fields from one block state. eth_getCAS20TokenInfoBatch accepts an address array with at most 20 entries and returns null for non-tokens; the single method errors for non-tokens. These RPC methods require Jenner at the selected block and are specific to supporting nodes.
core/vm/cas20_test.go:19
For codebase experiments, the test harness explicitly enables Jenner and Parlia on a copied test configuration; factory tests seed activation state directly. Those fixtures bypass the public governance setup to isolate behavior and are not a recipe for activating a live network. A complete application flow is: check chain/fork and feature activation, encode tuple params, predict address, create, verify the receipt and initialized token, grant operational roles, mint, transfer, then inspect balances and configuration.
